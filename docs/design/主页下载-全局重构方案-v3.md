# 主页下载 · 全局重构方案（v3）

> 版本：2026-10-10 初稿 · 状态：**P1/P2/P3 主体已落地并验收（v3.0.12）**，剩登录引导页与快红主页支持
> 触发：用户报「主页下载不了了」（`https://v.douyin.com/f1xouOxEGDw/`）+ 要求全局重新优化
> 前身：`主页批量下载功能设计.md`（v2，2026-09-05）——本文档是它的**架构级修订**
>
> **结论速览**：真根因不是「WebView 被软风控」，而是 WebView 的 **`navigator.platform` 与 UA 声明的平台不一致**
> → 服务端返回 `200 + 空 body`。修复 = 注入桌面环境自洽补丁（§1.8）。修复后匿名可取 21 条并全部下载成功。

## 1.6 决定性对照实验（CDP 无头浏览器，2026-10-10）

为了把「到底缺什么」问到底，用 CDP 对无头 Chrome 做了三组实验。

### 实验 0 · 入口页二选一（**推翻了 4.2 的初稿结论**）

| 入口 | 匿名加载表现 |
|---|---|
| `m.douyin.com/share/user/{sec_uid}`（移动 UA） | ❌ 未水合：`<a>` 标签 **0 个**、滚动后 HTML 长度不变、`_ROUTER_DATA.loaderData["user_(id)/page"]` 为空壳（len 7217，`hasPlayAddr:false`）、`_SSR_DATA` 仅 303 字节 |
| `www.douyin.com/user/{sec_uid}`（桌面 UA） | ✅ 完整水合，页面**自己发起** `GET /aweme/v1/web/aweme/post/` → **200** |

→ **入口必须用桌面版** `https://www.douyin.com/user/{sec_uid}`（与 App 现有 `BgWebViewParser` 的桌面 UA 策略一致）。移动版没有可嗅探的 post 请求。

### 实验 1 · 全新匿名会话能否拿到直链

用 `Target.createBrowserContext` 开**独立浏览器上下文**（零历史 cookie），加载桌面用户主页：

| 观察项 | 结果 |
|---|---|
| `GET /aweme/v1/web/aweme/post/?...&sec_user_id=...` | **200** |
| 响应体 | **1,074,727 字节** |
| `aweme_list` | **21 条**，`has_more: 1`，`max_cursor: 1788512523000` |
| 首条 | `aweme_id 7627065155646253706`、desc `#jk穿搭` |
| 首条直链 | `https://v26-web.douyinvod.com/.../video/tos/cn/tos-cn-ve-15/okjQkjV7EIPcqvGMlIaiAY...` ✅ |
| 字段完整度 | 含 `play_addr` / `aweme_images` / `item_list` / `url_list`，**与桌面版同构** |
| 自动种下的 cookie | `UIFID_TEMP` `ttwid` `odin_tt` `__ac_nonce` `__ac_signature` `s_v_web_id` `bd_ticket_guard_client_data` `bd_ticket_guard_regenerate_keys_time` `__security_mc_1_s_sdk_crypt_sdk` `passport_csrf_token` … |

**→ 匿名、零历史状态即可拿到 21 条含直链的完整数据。登录非必需。**

### 实验 2 · cookie 是不是充要条件（**根因定位的决定性一步**）

拿实验 1 抓到的**完整 post URL**（含 `a_bogus`、`msToken`）做 HTTP 重放：

| 实验 | 条件 | 结果 |
|---|---|---|
| **A** | 完整 URL + 真实 cookie + 桌面 UA | **200 / 1,075,156 字节 / 21 条** ✅ |
| **B** | 同 URL，**仅去掉 Cookie 头** | 200 但 **body 长度 0** |

**结论（根因锁定）**：

1. **a_bogus 不是瓶颈** —— App 的纯 Kotlin `DouyinAbogus` 已过 Python 金标准；URL 签名自洽即可。
2. **cookie 才是充要条件** —— 缺 cookie 时服务端返回 **200 + 空 body**（这正是 App 里 `parsePostListJson` 判 blocked 的形态）。
3. App 的 `warmupAndSnapshot` 走的是**轻量首页 `/`**，只能种下 `UIFID_TEMP`（logcat 实证：`cookie=2099字符 含UIFID_TEMP`），**拿不到** `__ac_signature` / `bd_ticket_guard_client_data` / `__ac_nonce` —— 这几个必须由**页面 JS 多轮执行**（secsdk）才生成。所以 post API 被 Argus 拒。

### 实验 2 顺带解锁的更优架构

实验 A 证明：**只要 cookie 齐，纯 HTTP 就能续翻页**。于是最优形态不是"全程 WebView"，而是：

```
WebView 只做首屏（过安全门 + 种下完整 cookie + 产出第 1 页 21 条）
        ↓ cookie 同步进 CookieManager / max_cursor 取回
纯 HTTP 按 max_cursor 续翻后续页（快，秒级）
        ↓ 若续翻再被拦
回退 WebView 滚动嗅探补页
```

即 **「WebView 破门 + HTTP 翻页」**：把最贵的 WebView 渲染限制在 1 次，后续翻页全部走轻量 HTTP。这是 4.2 实现时的目标形态。

## 1.7 补充实验（同日，三组，推翻 §1.6 的两条推论）

### 实验 3 · cookie 子集隔离 → **只需 `ttwid`**

对抓到的完整 post URL（含 a_bogus）逐组删 cookie 重放：

| 保留的 cookie | 结果 |
|---|---|
| 全量 28 个 | 200 / 21 条 |
| 去 `bd_ticket_guard_client_data` | 200 / 21 条 ✅ |
| 去 `__ac_signature` | 200 / 21 条 ✅ |
| **去 `ttwid`** | 200 / **0 条** ❌ |
| 去 `__ac_signature` + `bd_ticket_guard_client_data` | 200 / 21 条 ✅ |
| **仅 `ttwid` 一个** | **200 / 21 条** ✅ |
| 空 | 200 / 0 条 |

**结论**：cookie 侧唯一必需的是 `ttwid`。§1.6 推论的「必须凑齐安全 cookie 链」**过度严格**——
实现上若把 `__ac_signature` / `bd_ticket_guard_client_data` 也列为必需，会导致预热在部分机型
（这两者永不出现在 CookieManager 里）**空等满预算**。→ 代码已改为 `POST_API_REQUIRED_COOKIES = ["ttwid"]`。

### 实验 4 · 参数差分 → **L1 在架构上已死**

把浏览器实际发出的 post 请求（**45 个参数**）与 App 自建请求（约 24 个）做差分，浏览器独有：

| 参数 | 性质 |
|---|---|
| **`uifid`** | 页面 secsdk 产出 —— App 报错里的 `Uifid Not Found` 正是指它 |
| **`x-secsdk-web-signature`** | secsdk 生成的**第二个签名**（除 a_bogus 外） |
| `webid` / `verifyFp` / `fp` / `timestamp` | 风控指纹 |
| `from_user_page` / `time_list_query` / `cut_version` / `version_code` / `version_name` | 语义参数 |

**结论**：post 请求需要的**不止 a_bogus**，还有 `uifid` 与 `x-secsdk-web-signature` 这类
只能由页面 secsdk JS 运行产出的值。**纯 HTTP + 自算 a_bogus 无法补齐**——L1 不是"暂时被拦"，
而是**结构性不可用**。§1.6「HTTP 续翻」的推论随之作废。

### 实验 5 · a_bogus 是否可复用 → **否，严格绑 query**

| 请求 | 结果 |
|---|---|
| 原 URL 重放 | 200 / 21 条 |
| 改 `max_cursor`（a_bogus 不变） | **403** |
| 坏 a_bogus | 403 |
| 删 a_bogus | 403 |

**结论**：a_bogus 严格绑定 query，**改任何参数即 403**，不能截获后复用于翻页。
顺带得到一个**可区分两种失败的判据**：

| 失败形态 | 含义 |
|---|---|
| **403**（短 body） | 签名/参数不合法（a_bogus 或 uifid 缺失） |
| **200 + 空 body** | cookie 不足（缺 `ttwid`） |

### 实验 6 · 匿名上限 → **21 条（服务端限制）**

页面底部实测文案：**「登录后查看更多作品」**；SSR 数据里 `awemeCount: 253`，
但匿名只返回首屏 **21 条**（`has_more:1`）。用真实滚动（`Input.synthesizeScrollGesture`）
与容器 `scrollTop` 两种方式**均无法触发第二页**——因为这里是登录墙，不是懒加载。

**结论**：**匿名只能取到最近 21 条**。这不是 bug，是抖音的产品限制。产品必须正面处理：
- 匿名：给出「已获取最近 21 条（共 253 条）」的明确提示
- 想要全部：引导登录（登录后嗅探可继续翻页）

## 1.8 根因锁定：环境指纹不自洽 → 服务端 200+空 body（2026-10-10 修正）

> 本节先前版本结论为「Android WebView 环境整体被软风控」，**该结论已被证伪并推翻**。
> 下面是重做对照实验后的真实根因。

### 现象

L2a 嗅探工程上跑通（钩子安装成功、截到页面自己发出的 post 请求、`uifid` / `x-secsdk-web-signature` /
`a_bogus` / `msToken` / `webid` 全齐），但响应是：

```
post_resp status=200 len=0          ← 200 但空 body（不是 403，状态码完全看不出问题）
```

### 决定性对照实验（CDP，每条独立匿名 context，全部伪装 Windows Chrome/124 桌面 UA）

| # | 变量（相对基线只改一项） | status | body 字节 | 作品数 |
|---|---|---|---|---|
| A | `navigator.platform = Win32`（自洽·基线） | 200 | 1,047,917 | **21** |
| **B** | **`navigator.platform = Linux x86_64`** | 200 | **0** | **0** ← 单变量复现 App 故障 |
| C | WebGL renderer 改 `WebKit WebGL` | 200 | 1,048,833 | 21 |
| D | WebGL renderer 改 `Adreno (TM) 730` | 200 | 1,074,353 | 21 |
| E | 全安卓自洽（安卓 UA + armv8l + Adreno + 移动屏） | — | — | 页面**不发** post 请求 |

### 结论

1. **触发条件是 `navigator.platform` 与 UA 声明的平台不一致**，且是唯一的决定性变量。
   本 App 的 WebView 用 `DESKTOP_UA`（`Windows NT 10.0`）却暴露 Android 的
   `navigator.platform`（`Linux armv8l`/`x86_64`）→ 服务端**静默拒绝**：返回 200 + 空 body。
2. **WebGL 渲染器 / CPU 核数 / 内存 / 屏幕尺寸 / cookie 内容 均非触发条件**（C/D 及更早的
   核数内存对照全部正常）。先前把「`chrome=false`、`device_memory=2`、`pc_libra_divert=Linux`」
   当作嫌疑，属误判。
3. **不是「WebView 被软风控」**——同一个 WebView，只要把 `platform` 对齐成桌面身份即可取到数据。
   所以修复方向是**环境自洽**，不是放弃 WebView。
4. 纯安卓身份（E）在本入口页拿不到数据：页面路由到移动版、压根不发 post 请求。
   故**桌面身份 + 环境自洽**是正解，而不是「换移动 UA 蒙混」。

### 修复

新增 `app/src/main/assets/douyin_desktop_env.js`，在页面主 JS **之前**注入，把环境信号
统一成与 `DESKTOP_UA` 一致的 Windows 桌面 Chrome：

| 项 | 改为 | 理由 |
|---|---|---|
| `navigator.platform` | `Win32` | **决定性变量**，必须与 UA 一致 |
| `navigator.maxTouchPoints` / `ontouch*` | `0` / 移除 | Windows 桌面 Chrome 无触摸能力 |
| `navigator.userAgentData.platform/mobile` | `Windows` / `false` | UA-CH 与 UA 一致 |
| `screen.*` | `1920×1080` / depth 24 | 与桌面 UA 相称 |
| `navigator.language(s)` | `zh-CN` | 与 UA 声称的中文区一致 |

注入点（幂等守卫 `__dyDesktopEnv`）：
- `sniffOnce` 的 `onPageStarted` **与** `onPageFinished`，顺序在 `SNIFF_ASSET` 之前；
- `warmupAndSnapshot` 的 `onPageStarted`（secdsk 种 cookie 时同样读环境信号）。

**方法论教训**：把「整类环境」笼统归因为软风控，会掩盖真正可修的单变量。正确做法是**逐个变量
做单变量对照**——本例中 5 个候选里只有 1 个是真凶。

## 2. 根因（不是 bug，是架构脆弱性）

现架构的隐含假设：**「本地自算签名（a_bogus）+ 自己种 cookie 指纹」能长期对抗抖音风控**。

实测表明该假设已不成立：
- a_bogus 是抖音私有算法，**每次迭代都要逆向跟进**（历史上已跟过多次）
- 现在还要 msToken、UIFID、ttwid 等一串指纹，缺一个就 403
- 落地页从「SSR 带数据」转向「纯 JS 异步拉取」→ 所有抠 HTML 的兜底路径集体失效

**单点依赖 + 持续对抗 = 周期性失效**。这就是「又要修一次」的根。

## 3. 方案选型

| | A. WebView 网络嗅探 | B. 补强 API 自算签名 | C. 分层降级（推荐） |
|---|---|---|---|
| **原理** | 离屏 WebView 加载作者主页，JS hook `fetch`/`XMLHttpRequest`，把**抖音自己请求到的** `aweme/post` 响应体截下来 | 补齐 msToken/UIFID + 升级 a_bogus + 强化 warmup | L1 API 直取 → L2 WebView 嗅探 → L3 登录引导兜底 |
| **稳定性** | 🟢 高——签名由抖音页面 JS 自己算，它改版我们不跟 | 🔴 低——每次风控升级都要逆向跟进 | 🟢 高（L1 挂了自动走 L2） |
| **速度** | 🟡 3~8s（要渲染页面） | 🟢 <2s | 🟢 能用 L1 就快 |
| **维护成本** | 🟢 低 | 🔴 高（持续对抗） | 🟢 低 |
| **风险** | 离屏 WebView 内存/进程回收；仍需登录态 | 随时再挂 | 实现量稍大 |
| **结论** | 核心兜底路径 | 保留为 L1 快路径 | ✅ **推荐** |

**推荐 C 的核心理由**：把「签名对抗」的包袱丢回给抖音自己的页面。我们只蹭它算好的请求，不再维护 a_bogus 版本跟进。

## 4. 推荐方案详细设计

### 4.1 架构：Repository + Provider 链（可插拔）

```
HomepageRepository.resolve(secUid) : HomepageFeed
  ├─ L1  PostApiProvider      ← 现有 fetchPostList（快探一次；实测结构上必 403，保留作低概率回退）
  ├─ L2a WebViewSniffProvider ← 【主路径】hook XHR/fetch 截页面自己的 post 响应（不重算任何签名）
  ├─ L2b DomScrapeProvider    ← 滚动/点击抠 /video/{id} 链接，逐条解析（L2a 失效时最后兜底）
  └─ L3  LoginProvider        ← 引导登录：解锁第 2 页起（匿名上限 21 条，见 §1.7 实验 6）

每个 Provider 返回 sealed Result：
  Success(items, cursor, hasMore, totalCount) | Blocked(原因) | Empty | Failed(原因)
Repository 顺序尝试，记录每级失败原因 → 用于分级提示 + 埋码
```

**为什么没有 L1'（HTTP 续翻）**：实验 5 证明 a_bogus 严格绑 query，不能截获复用；实验 4 证明
自建请求还缺 `uifid` / `x-secsdk-web-signature`。故**任何翻页都必须由页面自己发起**，
L2a 拿到多少算多少（匿名 21 条），更多只能靠登录。

### 4.2 L2 WebView 嗅探（核心技术点）

**入口页（实测选定，见 §1.6 实验 0）**：`https://www.douyin.com/user/{sec_uid}`（**桌面版**）
- 桌面版会**自己发起** `/aweme/v1/web/aweme/post/`，这是唯一可嗅探到直链的入口
- 与 App 现有 `BgWebViewParser` 的桌面 UA 策略天然一致
- ❌ **不要用** `m.douyin.com/share/user/{sec_uid}`：实测该壳页在无头/离屏环境**不水合**，无可嗅探请求

**L2 内部分两路（主 + 兜底）**：

| 路线 | 做法 | 数据完整度 | 优先级 |
|---|---|---|---|
| **L2a 响应嗅探（主）** | JS hook `fetch` + `XMLHttpRequest`，截 `/aweme/v1/web/aweme/post/` 响应体 → 一次拿到 **21 条**含 `play_addr`/`aweme_images` **直链**的完整 JSON | 🟢 高（aweme_list 全字段，与桌面版同构，已实测） | 首选 |
| **L2b DOM 抠 id（兜底）** | 滚动触发懒加载，从 DOM 抠 `/video/{id}`、`/note/{id}` 链接，再逐条走单作品解析 | 🟡 仅 id，需二次解析（慢 N 倍） | L2a 失败时 |

**技术实现要点（L2a）**：
- **注入时机**：`onPageStarted` 立即 `evaluateJavascript` 注入 hook（早于抖音主 JS 执行）；`onPageFinished` 再注入一次（幂等守卫）兜底
- **hook 方式**：包裹 `window.fetch` 与 `XHR.prototype.open/send`，**只读不改**（不得影响页面自身逻辑，否则页面自己就坏了）
- **回传**：hook 内经 `addJavascriptInterface` Bridge 把**裁剪后**的 JSON（只留直链相关字段，
  约 15~20KB）丢回原生 —— **不要回传原始响应体**（约 1.05MB，跨 JS↔Java 桥开销大且无必要）。
  裁剪结构刻意做成与 post 接口同构，原生侧可直接复用 `DouyinParser.parsePostListJson`。
- **cookie 同步**：嗅探同时页面会种下完整 cookie（含 `ttwid`），CookieManager 全局生效，惠及单作品路径
- **翻页**：❌ **不做**。实验 6 证明匿名上限 21 条（登录墙），滚动/点击均无效；
  `has_more:1` 仅用于提示用户「更多需登录」，不再尝试翻页
- **超时**：总预算 35s；拿到 ≥1 页即**提前返回**（不等预算耗尽）
- **⚠️ UA 一致性**：签名与 UA 绑定。L2a 不重算签名，故无此风险；但若将来恢复任何自算签名路径，
  必须确保其 UA 与 WebView 种 cookie 时的 UA 一致

### 4.3 凭据与登录态（定位修正 · 二次修订）

第一次修订说「登录不是必需」，**实验 6 后又修正为更准确的表述**：

| 能力 | 匿名 | 登录后 |
|---|---|---|
| 作品列表 | ✅ 但**仅首屏 21 条** | ✅ 可翻页拿全部（253 条量级） |
| 直链（play_addr / images） | ✅ 首屏即含 | ✅ |
| 作者昵称 / 作品总数 | ✅ | ✅ |

- **登录的角色**：把「21 条」提升为「全部」。这是**产品级差异**，不是细节。
- **必须正面告知**：匿名取到 21 条而账号有 253 条时，UI 明确显示
  「已获取最近 21 条（该账号共 253 条作品，更多需登录抖音后查看）」，而不是静默截断。
- **文案修正**：旧文案「需要登录抖音：请先…」把**结构性失败**误报成**登录问题**，已改为
  「接口被抖音风控拦截，备用通道也未能取到作品。可稍后重试，或…登录后再试」。
- 保留 CookieManager 持久化 + `warmupAndSnapshot`（对**单作品** detail 路径仍有价值）。

### 4.4 交互层优化（"全局"含义）

| 场景 | 现状 | 目标 |
|---|---|---|
| 解析中 | 只有一个 Loading | 进度可见：`正在获取列表…（已发现 23 条）` |

| 范围选择 | ONLY_NEW/ALL/LATEST_N | 保留 |
