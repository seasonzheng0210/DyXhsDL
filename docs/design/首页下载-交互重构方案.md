# 首页下载 · 交互重构方案（v2 · 含入口层）

> 版本：2026-10-10 v2 · 状态：待拍板
> 触发：用户报「交互设计需要重构」→ 第一版只设计了页面内部 → 用户补充：
> **「我刚进来时肯定是复制了主页分享的链接进来，这时候识别跳到的地方和标签页的主页下载是同个地方；
> 其次我也可以自己主动粘贴；也可以在单个任务里跳到主页下载」**
> 配套 mockup：`首页下载-交互重构-mockup.html`

---

## 0. 结论先行

要分两层看，**入口层的问题比页面层更严重**：

| 层 | 一句话结论 |
|---|---|
| **入口层（本次新增）** | `fetchHomepagePreview` 只做**数据写入**，不做**导航**。**6 个入口共用它，其中 5 个不切换页面** → 用户"识别到了但什么都没发生"。而 App 默认落地页恰恰是**任务页**。 |
| **页面层（v1 已给）** | 配置、内容、主操作三层揉进同一条滚动流 → 主按钮要上滑 5 次才能找到。 |

**核心设计决策**：**主页下载只有一个承载面**（首页下载 tab 的同一状态机），**所有入口走同一条导航通道** `openHomepage(link, from)`。

---

## 1. 入口与流转

### 1.1 现状：6 个入口，只有 1 个能看见结果

| # | 入口 | 代码位置 | 现状 | 用户实际感受 |
|---|---|---|---|---|
| **E1** | 剪贴板自动识别（ON_RESUME） | `checkClipboard` L321-328 | 调 `fetchHomepagePreview(clipText)`，**无 `mainTab = 0`** | 复制链接回到 App → **什么都没发生** |
| **E2** | 剪贴板悬浮球 | `onWebCrawlFromClipboard` L653+ | 同上，无 `mainTab = 0` | 同上 |
| **E3** | 任务卡长按 →「主页下载」 | L2784 → L2117 → L466 | 同上，无 `mainTab = 0` | **点了看起来没反应**；且长按本身不可发现 |
| **E4** | 单作品短链 302 到 `/user/` | `launchDouyinWebView` L842 | 同上 | 停留原页 |
| **E5** | 主页批次任务重试 | `onRetryTask` L604 | 同上 | 停留原页 |
| **E6** | 主动粘贴（首页下载 tab） | `HomepagePage` L3116 | 原地渲染 | ✅ **唯一正常** |
| — | 任务**详情页** | `TaskDetailActivity` L213 | 只弹 toast「主页批量请在「首页」重新解析该主页」 | **入口缺失**，文案还把用户赶去手工操作 |

### 1.2 三个决定性事实

**事实 1：默认落地页是任务页，且识别不切页。**
```kotlin
var mainTab by remember { mutableStateOf(1) }   // L257：默认进任务
// checkClipboard：
if (UrlUtils.isDouyinHomepageLink(clipText)) {
    fetchHomepagePreview(clipText)               // ← 全程没有 mainTab = 0
}
```
`fetchHomepagePreview` 内部只写 `homePreview = Loading / Ready`，**从不碰 `mainTab`**。
→ 用户复制主页分享链接回到 App，解析在后台跑完 11~14 秒，**屏幕上什么都没有**。这是当前最严重的隐性缺陷。

**事实 2：「任务 → 主页下载」入口已存在，但它坏了。**
任务卡长按菜单里确实有「主页下载」项（`menuActions` 在 `isDouyinTask` 时 add `"homepage"`），链路是
`L2784 onHomepageDownload()` → `L2117 onHomepageDownload(task.noteUrl)` → `L466 fetchHomepagePreview(link)`。
**唯一的问题就是没切页** —— 所以功能是好的，"看起来没反应"是纯导航缺陷。

**事实 3：用户真正会去的地方（任务详情页）没有这个入口。**
点任务卡进的是 `TaskDetailActivity`，而它只有那句把用户赶走的 toast。**长按不可发现 + 详情页缺失**，导致这个本该顺手的动作等于不存在。

### 1.3 设计：唯一入口通道 + 唯一承载面

```
   ┌─ E1 剪贴板识别 (ON_RESUME)
   ├─ E2 悬浮球
   ├─ E3 任务卡长按「主页下载」
   ├─ E4 单作品短链 302 → /user/
   ├─ E5 主页批次任务重试
   ├─ E6 主动粘贴 / 最近作者
   └─ E7 任务详情页「下载该作者的主页」   ← 本次新增
                │
                ▼
      openHomepage(link, from)            ← 唯一入口函数（替代 6 处 fetchHomepagePreview）
                │
                │  1) if (mainTab != 0) { returnTab = mainTab; mainTab = 0 }   ← 先导航
                │  2) homePreview = Parsing(link)                              ← 立刻可见
                │  3) 解析（三阶段、可取消）
                │  4) homePreview = Ready
                ▼
   首页下载 tab · S2 就绪屏                ← 唯一承载面
```

`from` **只决定两件事**：顶部来源条文案、返回按钮的去向。**不改变承载面**。

### 1.4 七种入口的行为矩阵

| `from` | 来源条 | 返回动作 | 备注 |
|---|---|---|---|
| `clipboard` | 🔗 已识别剪贴板的主页链接 | 回到识别前的 tab（并还原剪贴板） | 识别后清剪贴板；记 `returnTab` |
| `bubble` | 🔗 来自剪贴板悬浮球 | 同上 | 同上 |
| `taskCard` | ← 来自任务：<作品标题> | 回任务页并滚到该任务卡 | 传 `sourceTaskId` |
| `taskDetail` | ← 来自任务：<作品标题> | 回该任务详情页 | 传 `sourceTaskId` |
| `shortlink` | ℹ 这是作者主页，已转为批量下载 | 回识别前的 tab | — |
| `manual` | —（不显示） | — | 无导航，原地 |
| `recent` | —（不显示） | — | 无导航，原地 |

**为什么必须有「返回」**：识别会打断用户当前在做的事。没有返回，被弹到首页下载后想回去要多点几次；有返回，成本降到 1 次点击。这也是为什么**不采用"先弹确认条"**——把成本留给 5% 的误触（用「返回」兜住），而不是加到 95% 的正确情况上。

### 1.5 新增能力：任务 → 该作者主页

现状缺口：`TaskDetailActivity` 里**没有**入口，只有 toast；`DownloadTask` **没有** `authorSecUid` 字段。

设计：
1. `DownloadTask` 新增 `authorSecUid: String? = null`，解析单作品时从 detail/post 响应的 `author.sec_uid` 落库（老任务为 null，向后兼容）
2. `TaskDetailActivity` 的**下载中 / 已完成 / 失败**三态卡统一新增一行：
   ```
   ⬇ 下载该作者的主页        ›
     还可下载该博主全部作品
   ```
   仅在 `source` 为 `douyin` / `douyin_home` / `kuaishou` 时显示（小红书本期不支持）
3. 点击行为：
   - 有 `authorSecUid` → `openHomepage("https://www.douyin.com/user/$secUid", from = taskDetail)`
   - 无（老任务）→ `openHomepage(task.noteUrl, from = taskDetail)`，由入口通道内部的「反查作者主页」补上（这一段耗时正好被 Parsing 的第一阶段「打开作者主页」掩盖）
   - `source == "douyin_home"` 的批次任务 → 文案改为「**重新检查新作品**」，直接 `openHomepage(task.noteUrl, from = taskDetail)`
4. **删掉** L213 那句「主页批量请在「首页」重新解析该主页」——不再有"让用户去别处手工操作"的文案

### 1.6 跨 Activity 导航实现

`TaskDetailActivity` 是独立 Activity，主页下载承载面在 `MainActivity`。通道：

```kotlin
// TaskDetailActivity
Intent(context, MainActivity::class.java).apply {
    addFlags(Intent.FLAG_ACTIVITY_CLEAR_TOP or Intent.FLAG_ACTIVITY_SINGLE_TOP)
    putExtra(MainActivity.EXTRA_OPEN_HOMEPAGE, url)
    putExtra(MainActivity.EXTRA_SOURCE_TASK_ID, task.id)
}
// MainActivity：onNewIntent 里统一转 openHomepage(url, Entry.TaskDetail(taskId))
```

`MainActivity` 需在 Manifest 声明 `android:launchMode="singleTop"`（或用 `CLEAR_TOP` 复用栈内实例），避免重建。

## 2. 页面内部根因（v1 结论，保留）

| # | 根因 | 证据 |
|---|---|---|
| R1 | 主操作被放进滚动流 | 「确认下载」是 `HomepagePage` 里 `Column.verticalScroll` 的**最后一个子节点** → 实测要上滑 **5 次** |
| R2 | 两种选择语义混进同一单选列表 | 策略（仅新增/全部/最近N）与枚举（按勾选）平铺；且「包含图文 / 跳过已下载」在 SELECTED 档被**静默忽略**（代码注释写了 ignore）；点网格会偷偷切档而无提示 |
| R3 | 长任务零信息量 | 解析实测 11~14s，`HomePreviewState.Loading` 是无阶段的 `data object`，且**不可取消** |
| R4 | 硬约束事后解释 | 253 条只给 21 条 + 11sp 灰字解释 → 这正是本次报障的心理起点 |
| R5 | 回访场景没被当主场景 | `HomeRepo.lastUsed` 已存在，但只在 Idle 态渲染一张卡 |

> 注意 R3 与入口层的耦合：解析要 11~14 秒，但**入口不切页**，所以用户连"它在转"都看不到 —— 两个缺陷叠在一起才是"主页下载坏了"的完整体感。

## 3. 状态机

```
                   openHomepage(link, from)      ← 所有入口唯一通道
                            │
   Idle ─────────────────► Parsing ──成功──► Ready ──确认──► Downloading ──► Done
    ▲                       │                │  ▲                              │
    │                       │取消/失败        │  │ 选片页返回（回写选中集）      │
    │                       ▼                ▼  │                              │
    └── 取消保留已填链接 ◄────┘            Picker ┘                              │
    ▲                                                                          │
    └────────────────── 返回（回到 returnTab） / 再检查 / 换作者 ◄───────────────┘
```

`Ready` 是唯一枢纽态；`returnTab` 与 `sourceTaskId` 随会话存活，直到用户点「返回」或被新入口覆盖。

## 4. 页面结构：常驻操作条

```
┌──────────────────────────────────────┐
│ 抖快红下载                            │  顶栏
├──────────────────────────────────────┤
│ 🔗 已识别剪贴板的主页链接      返回 › │  来源条（仅非 manual 入口显示，可关）
├──────────────────────────────────────┤
│   ┌ 滚动流：只放「内容」 ┐             │
│   │  · 作者摘要        │             │
│   │  · 下载计划卡      │             │
│   │  · 作品预览        │             │
│   └───────────────────┘             │
├──────────────────────────────────────┤
│ 将下载 18 个          [  开始下载  ]  │  常驻操作条（sticky）
├──────────────────────────────────────┤
│  首页下载 |  任务  |  设置            │  dock
└──────────────────────────────────────┘
```

**分层规则**：滚动流只承载**阅读性内容**；「改变即将发生的事」的控件走 **bottom sheet**；「推进流程」的按钮进 **常驻操作条**。

### 4.1 常驻操作条状态矩阵

| 状态 | 左侧 | 主按钮 | 可点 |
|---|---|---|---|
| Parsing | `正在解析…` | `取消` | ✓ |
| Ready（策略档） | `将下载 18 个 · 跳过 3 个` | `开始下载` | ✓ |
| Ready（手选 12 个） | `已选 12 个` | `下载已选` | ✓ |
| Ready（新增 0 个） | `没有新作品` | `开始下载`（禁用但保留） | ✗ |
| Downloading | `下载中 12 / 18` | `去任务页` | ✓ |
| Done | `完成 17 个 · 失败 1 个` | `查看任务` | ✓ |

> 「没有新作品」时主按钮**禁用但保留** —— 位置稳定比省空间重要（避免按钮忽隐忽现导致误触）。

## 7. 权衡与取舍

| 决策 | 取 | 舍 | 理由 |
|---|---|---|---|
| 入口一律**先导航再解析** | 结果必然可见 | 会打断用户当前页 | 不导航 = 白跑 11~14 秒且用户以为坏了；用「返回」兜住打断成本 |
| **不弹确认条**，识别后直接解析 | 主路径最短（符合"意图明确"） | 5% 误触会白跑一次 | 解析可取消，取消后**保留已填链接**；把成本放在少数 |
| 主页下载**保留为 tab** | 有稳定入口、支持回访 | tab 与"唤起式流程"的语义不完全匹配 | 它是"发起 + 回访"双属性；拆成 sheet 会失去回访入口，改动也更大 |
| 主操作条常驻 | 位置稳定性 | 约 72px 垂直空间 | 找不到主按钮是**阻断性**问题 |
| 网格下沉二级页 | 主路径短 | 挑作品多一次跳转 | 挑作品是少数场景，不该让主线承担其成本 |
| 任务详情页也放入口（不只在长按菜单） | 可发现性 | 详情节多一行 | 长按不可发现 = 功能等于不存在 |
| `authorSecUid` 落库 | 跳转零网络开销 | 需改数据类 + 兼容老数据 | 每次跳转都反查要一次网络跳转，体验差 |

## 8. 验收口径

| 项 | 标准 |
|---|---|
| **入口收敛** | 7 个入口触发后，**无需任何额外操作**，1 屏内可见作者摘要与「开始下载」 |
| **默认页签兼容** | 在任务页（默认）复制主页链接 → 回到 App → 自动落到首页下载 tab 且立即显示解析进度 |
| 返回路径 | 从任务入口进入后，**1 次点击**可回到原任务；从剪贴板入口进入后，1 次点击可回到原 tab |
| 主路径步数 | 粘贴 → 解析 → 开始下载 = **3 步，0 次滚动** |
| 主按钮可见性 | 任何状态、任何滚动位置下主按钮**始终可见** |
| 解析反馈 | 三阶段真实上报；任意时刻可取消，取消后 ≤1s 回到 Idle 且**保留已填链接** |
| 约束传达 | 解析完成 1 屏内可见「共 N 条 · 可取 M 条」，无需滚动 |
| 面板一致性 | 不存在「改了没反应」的控件：被忽略的组合必须有显式说明 |
| 文案审查 | 全 App **不存在**"请去别处手工操作"类文案（如 L213 那句） |
